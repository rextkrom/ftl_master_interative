Foundations

1. FTL의 존재 이유: NAND 플래시의 3대 물리적 한계

FTL(Flash Translation Layer)은 NAND 플래시 메모리의 하드웨어적 제약을 소프트웨어적으로 은폐하고, 호스트(OS, File System)가 SSD를 일반 바이트/섹터 블록 스토리지처럼 투명하게 사용할 수 있도록 지원하는 컨트롤러 핵심 펌웨어입니다.

💡 FTL이 극복해야 하는 하드웨어 3대 물리 법칙
  • 1. 덮어쓰기 불가 (No In-Place Update): 이미 기록된 셀에 새로운 데이터를 덮어쓸 수 없습니다. 기록 전 무조건 소거(Erase)가 선행되어야 하므로 변경 데이터는 항상 새로운 빈 위치에 기록해야 합니다 (Out-of-Place Update).
  • 2. 연산 단위의 비대칭성 (Unit Asymmetry): 읽기/쓰기는 페이지(Page, 4KB~16KB) 단위지만, 지우기는 수백 개 페이지가 묶인 블록(Block, 4MB~16MB) 단위로만 일괄 처리됩니다.
  • 3. 물리적 셀 수명의 한계 (P/E Cycle Limit): 쓰기/소거 시 고전압 터널링(Fowler-Nordheim)으로 절연 산화막이 열화되어 수명이 제한됩니다. (SLC: ~10만 회, TLC: ~1천~3천 회, QLC: ~수백 회).

L2P Address Mapping (논리-물리 주소 변환) ├─ 2. Garbage Collection (유효 데이터 회수 및 Free Block 확보) ├─ 3. Wear Leveling (마모도 균등화로 드라이브 수명 연장) └─ 4. Reliability Control (배드 블록 관리, Read Disturb/Retention 방어) ======▼============================================================= │ (PBA: Channel, Way/Die, Plane, Block, Page 물리 제어) [ NAND Flash Controller (Flash Bus, HW ECC Engine, Direct DMA) ]
Subsystem 1

2. 주소 맵핑 (L2P Address Mapping)

호스트가 요청하는 논리 주소(LBA)를 낸드의 실제 물리 주소(PBA)로 연결하는 핵심 테이블입니다.

Out-of-Place Update 동작 원리
  1. 호스트가 LBA 10번 데이터 갱신 요청
  2. FTL은 기존 물리 페이지를 지우지 않고, 빈 페이지(Free Page)에 새 데이터 기록
  3. 기존 물리 페이지를 무효화(Invalid) 처리
  4. 맵핑 테이블에서 LBA 10 ➔ 신규 PBA로 포인터 갱신

Subsystem 2

3. 가비지 컬렉션 (GC) & 쓰기 증폭 (WAF)

무효화(Invalid)된 찌꺼기 데이터가 누적되어 Free Block이 고갈되면, 유효 페이지만 새 블록으로 이주시키고 구 블록을 지워 빈 블록을 확보합니다.

[Victim Block A] : ❌ ❌ ✅ ❌ (Invalid 3개, Valid 1개) [Victim Block B] : ❌ ✅ ❌ ❌ (Invalid 3개, Valid 1개) │ ▼ [GC 발동: Valid Data 복사] [Target Block C] : ✅ ✅ ⬜ ⬜ ... (Free Block에 유효 페이지만 압축) │ ▼ [Erase 소거] [Block A, B] ➔ Erase 완료 후 새로운 Free Block Pool로 반환

쓰기 증폭 계수 (WAF, Write Amplification Factor):

WAF = (호스트 쓰기량 + GC 내부 복사 쓰기량) / (호스트 쓰기량)

※ WAF가 1.0에 가까울수록 이상적이며, WAF가 치솟으면 SSD의 쓰기 대역폭이 급락하고 P/E Cycle이 빠르게 소진됩니다.

Subsystem 3

4. 웨어 레벨링 (Wear Leveling)

특정 블록만 집중적으로 지워져 조기 사망(Premature Block Failure)하는 것을 방지하기 위해 전체 블록의 소거 횟수(Erase Count)를 평준화합니다.

  • 동적 웨어 레벨링 (Dynamic WL): 호스트가 새로 쓰는 데이터(Hot Data)를 할당할 때, Erase Count가 가장 적은 블록을 우선 할당.
  • 정적 웨어 레벨링 (Static WL): 한 번 기록된 후 거의 수정되지 않는 데이터(Cold Data, 예: OS 커널/라이브러리)가 점유한 건강한 블록을 발굴하여, Cold Data를 혹사당한 고마모 블록으로 강제 이사시키고 건강한 블록을 쓰기 풀로 회수.
Subsystem 4

5. 오버 프로비저닝 (OP) & TRIM

오버 프로비저닝 (Over-Provisioning): 사용자에게 노출하지 않고 FTL 백그라운드 관리 전용으로 숨겨둔 예비 물리 용량(보통 7%~28%). GC 시 버퍼 확보, 배드 블록 대체, WAF 억제에 결정적인 역할을 합니다.

TRIM (Deallocate) 커맨드의 본질

OS가 파일을 지워도 일반적인 파일시스템은 LBA 메타만 지울 뿐 SSD에 데이터를 통지하지 않습니다. TRIM은 "이 LBA 데이터는 더 이상 쓸모없다"고 FTL에 알려주어 즉시 Invalid 처리함으로써, GC 시 쓸데없는 복사를 방지하고 WAF를 극적으로 낮춥니다.

1. 3D BiCS NAND 물리 계층과 문턱 전압(Vth) 왜곡

SanDisk/Kioxia의 BiCS (Bit Cost Scaling) 3D Charge Trap Flash (CTF) 구조는 수백 단 높이로 셀을 쌓아 올리면서 물리적 노이즈와 셀 간 간섭이 극대화됩니다. FTL은 순수 알고리즘을 넘어 물리적 전압 특성을 소프트웨어로 통제해야 합니다.

Hardware / FTL Pipeline

2. LDPC ECC와 FTL Read Retry (Moving Read)

TLC/QLC에서는 Vth 분포가 겹치면서 통상 읽기(Normal Read) 실패가 빈번합니다. FTL과 하드웨어 엔진은 단계별 복구 파이프라인을 가동합니다.

[1. Normal Read] │ (Uncorrectable Error 발생) ▼ [2. LDPC Hard Decision] (하드웨어 비트 플리핑 반복) │ (Fail) ▼ [3. LDPC Soft Decision] (Soft Bit Read로 LLR 신뢰도 획득) │ (Fail) ▼ [4. FTL Moving Read Table (Read Retry)] │ ➔ FTL이 NAND 컨트롤러 레지스터를 직접 조작 │ ➔ 기준 전압(Vref) 오프셋을 단계별 이동 탐색 ▼ (Pass 성공 시) [5. Read Reclaim 스케줄링] (RBER 임계 초과 블록 데이터 신속 이주)
⚠️ RBER (Raw Bit Error Rate) 모니터링

Read Retry로 가까스로 복구된 블록은 하드웨어 수명이 한계에 다다른 상태입니다. FTL은 백그라운드 Read Reclaim 워커를 즉시 깨워 해당 블록의 데이터를 새 블록으로 복사합니다.

NAND Program Rules

3. Open Block 관리 & Sequential Wordline 제약

3D NAND의 물리적 커플링(Capacitive Coupling) 현상으로 인해 엄격한 프로그래밍 규칙이 적용됩니다.

  • Sequential WL Program: 한 블록 내부에서는 반드시 바닥 WL0부터 WLn까지 순차적으로만 기록해야 합니다. 역방향 기록이나 건너뛰기는 물리적으로 불가합니다.
  • Open Block (활성 블록): 아직 마지막 페이지까지 채워지지 않은 블록. Closed Block보다 외부 노이즈 및 Retention에 취약합니다.
  • Lower-Page Corruption 방어: TLC는 하나의 셀에 3비트(Lower, Middle, Upper)를 단계별로 기록합니다(Foggy-Fine Program). Upper 기록 도중 전원이 차단(SPO)되면 이미 완성되었던 Lower Page 데이터까지 물리적으로 파괴됩니다.
    ➔ FTL 대응: 핵심 메타데이터는 무조건 1-bit SLC 블록에 기록하고 저널을 유지합니다.
Reliability

4. 배드 블록 관리 (Bad Block Management, BBM)

공장 출하 시점에 존재하는 Initial Bad Block과 드라이브 런타임에 P/E Cycle 마모 또는 쓰기/지우기 실패로 발생하는 Runtime Bad Block을 격리 관리합니다.

런타임 배드 블록 격리 프로세스
  1. Program/Erase 수행 중 낸드 플래그 상태(Status Register) Fail 확인
  2. FTL 인터럽트 핸들러가 해당 블록을 즉시 Bad Block Table(BBT)에 등록 및 격리
  3. 기록 실패한 쓰기 버퍼 데이터는 예비 블록 풀(Reserve Pool)의 정상 블록에 즉각 리다이렉트 쓰기 수행
  4. BBT는 비휘발성 영역(NAND Meta Block)에 다중 복제(Duplicated)하여 영구 보존

Memory Architecture

1. Demand-based FTL (DFTL) & HMB

1TB SSD의 4KB Page Mapping에는 1GB의 DRAM이 필요하며, 8TB~16TB 대용량에서는 컨트롤러 비용과 전력이 감당 불가능해집니다.

[ Host LBA ] │ ▼ [ Cached Mapping Table (CMT) in DRAM/SRAM ] ───(Cache Miss 시) │ │ NAND에서 Translation ▼ (Hit) │ Page(TP) Swap-in [ Physical Address (PBA) ] ◀──────────────────────┘
  • Global Translation Directory (GTD): 각 변환 페이지(TP)의 낸드 물리 위치를 가리키는 소형 인덱스 테이블(메모리 상주).
  • Cached Mapping Table (CMT): 접근 빈도가 높은 L2P 엔트리만 메모리에 캐싱(LRU / ARC 알고리즘으로 스왑 관리).
  • NVMe HMB (Host Memory Buffer): DRAM-less 보급형 SSD에서 PCIe 버스를 통해 호스트의 메인 RAM(약 64MB)을 DMA로 직접 빌려와 CMT 캐시로 활용.
Hardware Parallelism

2. Superblock & Internal Die-RAID

단일 낸드 다이의 쓰기 속도는 수십 MB/s에 불과하지만, 고성능 SSD는 수 GB/s를 냅니다. 그 비결은 Superblock 가상화와 스트라이핑입니다.

Channel 0 Channel 1 Channel 2 Channel 3 (Parity) ┌───────────┐ ┌───────────┐ ┌───────────┐ ┌───────────┐ │ Die 0 Blk5│ │ Die 1 Blk5│ │ Die 2 Blk5│ │ Die 3 Blk5│ ➔ Superblock 0 └───────────┘ └───────────┘ └───────────┘ └───────────┘ [Data A] [Data B] [Data C] [XOR Parity]
SanDisk Guard: Die-Level RAID

슈퍼블록을 구성하는 다이 중 1~2개 다이의 블록을 XOR 패리티 블록으로 할당합니다. 특정 다이의 본딩 와이어 단선이나 다이 크랙으로 한 다이 전체가 영구 배드가 나더라도, FTL 내부의 Die-RAID 엔진이 나머지 다이 데이터와 XOR 연산하여 호스트 데이터 무손실 복구를 보장합니다.

Buffer Scheduling

3. Pseudo-SLC Caching & Folding Cliff

TLC 쓰기는 느리기 때문에, 1개 셀에 1비트만 쓰는 Pseudo-SLC 버퍼를 앞단에 전방 배치하여 호스트 쓰기 응답성을 높입니다.

  • Direct Folding: 유휴(Idle) 시간에 3개의 SLC 블록 데이터를 1개의 TLC 블록으로 직접 압축하여 복사.
  • Performance Cliff (성능 절벽): 연속된 대용량 쓰기로 SLC 버퍼가 100% 고갈되면, FTL은 [1] 호스트 쓰기, [2] SLC-to-TLC 폴딩, [3] TLC 가비지 컬렉션을 동시에 수행해야 하므로 속도가 1/10 수준으로 폭락합니다.
  • 피드백 루프 스케줄러: 시니어 펌웨어 아키텍트는 버퍼 점유율이 70~80%에 도달할 때 호스트 큐 전송을 미세 스로틀링하여 지연시간 편차(Jitter)를 방어합니다.
Latency Control

4. Program/Erase Suspend & Tail Latency

연산 종류소요 시간FTL 스케줄링 과제
NAND Read20 ~ 50 μs호스트 지연시간에 직결 (초고속 반환 필수)
NAND Program500 ~ 1,500 μsRead 대비 20~30배 느림
NAND Erase3,000 ~ 10,000 μsRead 대비 수백 배 느림 (Tail Latency 주범)
하드웨어 선점 (Preemption) 스케줄링

호스트 Read 요청이 들어왔을 때 해당 다이가 백그라운드 Erase(최대 10ms) 중이라면 99.99% 지연시간(Tail Latency)이 튑니다. FTL은 즉시 Erase Suspend 하드웨어 명령을 내려 지우기를 일시 중지하고, 수십 μs 내에 호스트 읽기를 먼저 처리한 뒤 Resume 명령으로 작업을 재개합니다.

Metadata Integrity

5. 서든 파워 오프 (SPO Recovery)

런타임 중 불시에 전원이 차단되었을 때 DRAM 휘발성 데이터를 잃지 않고 다음 부팅 시 무결성을 초고속 복구하는 아키텍처입니다.

  • Enterprise SSD (HW PLP): 탄탈륨 커패시터를 장착하여 전원 차단 후 20~50ms간 보조 전력을 공급. DRAM 캐시와 L2P 매핑을 낸드에 안전하게 일괄 플러시.
  • Client SSD (SW Checkpoint & Journaling): 커패시터가 없으므로 정전 즉시 다운.
    1) Checkpoint: 주기적으로 전체 L2P 스냅샷을 낸드 메타 블록에 저장.
    2) Journaling: 변경분(Delta L2P)만 로그 형태로 Append.
    3) 부팅 복구: 최신 Checkpoint 로드 후 Journal Replay를 실행하여 0.2초 내 완전 복구.
Next-Gen Standards

6. 차세대 NVMe 표준: FDP & ZNS 심층 분석

기존 FTL의 GC 부하와 WAF 문제를 해결하기 위해 호스트 OS와 SSD 컨트롤러가 협력하는 최신 NVMe 2.0 스토리지 표준입니다.

FDP (Flexible Data Placement, NVMe 2.0 TP4146)

ZNS와 달리 호스트 애플리케이션의 기존 블록 인터페이스(랜덤 쓰기)를 그대로 유지하면서도 WAF를 1.0으로 낮출 수 있는 혁신적인 기술입니다.

  • Reclaim Group (RG): 물리적 미디어(NAND 다이 및 채널)의 독립된 집합 단위.
  • Reclaim Unit (RU): 물리적 슈퍼블록에 대응되는 실제 데이터 소거(Erase) 단위.
  • RU Handle (RUH): 호스트가 쓰기 커맨드를 보낼 때 DTYPE(Data Type) 필드에 태깅하는 핸들. 호스트는 데이터 성격(Hot: RocksDB WAL 로그, Warm: Level-0 SSTable, Cold: Level-N SSTable)별로 서로 다른 RUH를 지정.
  • WAF 1.0 수렴 원리: FTL은 동일한 RUH를 가진 데이터끼리만 동일 슈퍼블록에 물리적으로 모아서 기록합니다. 결과적으로 같은 블록 내의 데이터들이 동시에 만료(Invalid)되므로 GC 시 살아있는 유효 데이터를 이사시킬 필요가 전혀 없어 WAF가 1.0에 수렴합니다.
ZNS (Zoned Namespaces) & 리눅스 커널 스택

호스트에게 수백 MB~수 GB 크기의 순차 쓰기 전용 Zone 인터페이스를 제공하여 FTL의 복잡한 Out-of-place 맵핑과 GC를 호스트 파일시스템(F2FS, RocksDB ZenFS, Ceph)으로 완전히 오프로딩합니다. SSD 내부의 대용량 DRAM 요구량을 90% 이상 제거할 수 있습니다.

Senior Staff Interview Q&A

시니어 스태프 인터뷰 핵심 질문 TOP 5 & 모범 답변 프레임

Q1. "FTL 코드를 직접 다뤄본 적이 없는데, 어떻게 Senior Staff 직무를 리드할 수 있는가?"

[모범 답변]: "FTL의 본질은 결국 '제한된 온칩 하드웨어 리소스와 비대칭적인 I/O 특성 하에서, 지연시간 편차 없이 데이터 무결성과 신뢰성을 보장하는 실시간 임베디드 스케줄러이자 가상 메모리 관리자'입니다. 저는 18년간 이종 멀티코어 환경에서 리소스 경합을 프로파일링하여 레이턴시를 안정화하고, 동적 메모리 할당을 엄격히 통제하여 무결점 스트레스 검증을 성공시킨 경험이 풍부합니다. 도메인 특화 세부 레지스터는 빠르게 흡수할 수 있으며, 시스템 레벨의 병목 돌파와 견고한 펌웨어 아키텍처 수립에 즉각 기여할 수 있습니다."

Q2. "가비지 컬렉션(GC) 시 발생하는 99.99% 최악 지연시간(Tail Latency / Jitter)을 어떻게 제어하겠는가?"

[모범 답변]: "단순히 GC 알고리즘을 빠르게 만드는 것만으로는 한계가 있습니다. 시스템 스케줄링 관점에서 접근해야 합니다.
첫째, 호스트 I/O를 처리하는 코어와 GC를 수행하는 코어 간의 Lock-free 비동기 큐잉을 구축합니다.
둘째, 백그라운드 지우기 작업 중 호스트 Read가 들어왔을 때 즉각 반응할 수 있도록 하드웨어 Erase Suspend 선점(Preemption)을 인터럽트 기반으로 구동합니다.
셋째, 버퍼가 고갈된 뒤 강제로 GC가 도는 최악의 상황을 방지하기 위해, SLC 버퍼 점유율에 따른 동적 크레딧 기반 쓰로틀링(Credit-based Throttling)을 적용하여 일정한 레이턴시를 유지시킵니다."

Q3. "제한된 컨트롤러 메모리 환경에서 대용량 L2P 매핑 테이블을 어떻게 아키텍처화 하겠는가?"

[모범 답변]: "DFTL(Demand-based FTL) 기법을 기반으로 설계하되, 런타임 메모리 단편화를 배제하기 위해 정적 슬롯 기반 External Buffer 풀을 구성합니다. 4KB Translation Page(TP) 단위로 플래시에 보관하고, 메모리 상주 인덱스(GTD)와 캐시 테이블(CMT)을 분리합니다. 캐시 교체 정책은 단순 LRU보다 시간적/공간적 지역성을 동시에 반영하는 ARC(Adaptive Replacement Cache) 계열을 경량화하여 적용하고, 캐시 미스 시 비동기 백그라운드 프리페치(Prefetching)를 통해 스왑 지연을 은폐합니다."

Q4. "Client SSD 환경에서 커패시터(PLP) 없이 서든 파워 오프(SPO) 발생 시 메타데이터를 어떻게 보장하는가?"

[모범 답변]: "비동기 Checkpoint & Journaling 2단계 구조를 채택합니다. 전체 L2P의 풀 스냅샷은 주기적으로 전용 메타 블록에 기록하고, 런타임 변경 내역은 1-bit SLC로 할당된 저널 블록에 순차 Append 로그로 기록합니다. 특히 TLC Open Block 기록 중 정전 시 발생하는 Lower Page Corruption을 막기 위해 저널과 커밋 마크를 철저히 분리합니다. 부팅 시에는 가장 최근의 유효 Checkpoint를 로드한 뒤 Journal Replay를 수행하여 수백 ms 내에 100% 무결성을 복원합니다."

Q5. "3D TLC/QLC에서 RBER이 급증하여 LDPC Hard/Soft Decision이 모두 실패할 때 FTL은 어떻게 대처하는가?"

[모범 답변]: "제어권이 FTL의 Dynamic Read Calibration 엔진으로 넘어옵니다. FTL은 낸드 컨트롤러의 DAC 레지스터를 직접 제어하여 기준 전압(Vref) 오프셋을 단계별로 미세 이동시키는 Moving Read Table을 순차 적용합니다. 데이터 복구에 성공하면 해당 블록의 RBER이 한계에 도달한 것으로 판단하여 백그라운드 Read Reclaim 작업을 즉시 큐잉하여 건강한 블록으로 유효 데이터를 신속히 이주시킵니다. 만약 이마저도 물리적으로 불가능할 경우, Superblock의 Die-RAID(SanDisk Guard) XOR 패리티 엔진을 가동하여 호스트 데이터 손실 없이 완벽히 복원합니다."

Test Design & Debugging

🧪 가혹 환경 검증 및 시나리오 설계

  • Sudden Power Interruption (PLP Injection): 랜덤 쓰기, GC 수행 중, 저널 Flush 도중 등 극단적 타이밍에 AC/DC 파워 릴레이를 수만 회 차단하여 데이터 무결성 및 부팅 복구 시간 검증.
  • High-Temperature Retention Aging: 드라이브를 챔버(85°C 고온)에 방치하여 셀 전하 누설을 인위적으로 유발한 후 백그라운드 Data Refresh 메커니즘 검증.
  • Extreme Corner-case Workload: 4KB 랜덤 쓰기 100% 포화 상태에서 TRIM과 호스트 Read를 동시에 폭격하여 Tail Latency Jitter와 Deadlock 여부 검증.

🔍 하드웨어 디버깅 & 버스 애널라이저 도구

  • PCIe / NVMe Protocol Analyzer (Teledyne LeCroy 등): 호스트와 컨트롤러 간 PCIe TLP 패킷, NVMe Submission/Completion Queue 타이밍, 크레딧 고갈 현상 실시간 캡처 및 분석.
  • JTAG & Hardware In-Circuit Emulator (ICE): 멀티코어 간 Lock 충돌, 하드웨어 Hang, ISR(인터럽트 서비스 루틴) 과점 현상 추적.
  • In-Memory Circular Event Tracer: 디버그 로그 출력으로 인한 타이밍 왜곡(Heisenbug)을 없애기 위해 고속 온칩 SRAM에 64바이트 컴팩트 바이너리 이벤트 로그를 링 버퍼로 기록.
Python Test Automation Framework

Python 기반 SSD Failure Injection Framework (Senior Staff 실무 코드)

시니어 스태프 펌웨어 엔지니어 JD의 필수 요건인 "Creative scenarios, test design, Python OOP, failure injection"을 완벽히 구현한 프레임워크 설계입니다. 드라이브 내부 상태(GC Copy 진행 상태)를 실시간 감지하여 가장 취약한 순간에 정전(PLP)을 인젝션하고 데이터 무결성을 폐루프(Closed-loop)로 자동 검증합니다.

# Python SSD Failure Injection Architecture (Senior Staff Framework) import time, logging from abc import ABC, abstractmethod class PowerRelayController: def cut_power(self): print("[HW-Relay] Main VCC Power Cut! (0V)") def restore_power(self): print("[HW-Relay] Power Restored (12V/3.3V)") class DataIntegrityOracle: def verify_lba_range(self, start_lba: int, count: int) -> bool: print("[Oracle] Verifying Golden Data vs Flash Contents...") return True # No Silent Data Corruption (SDC) class StateAwareGcPlpTest: """GC 수행 중 가장 취약한 Victim 블록 복사 타이밍에 정전을 유발하는 폐루프 테스트""" def __init__(self, psu: PowerRelayController, oracle: DataIntegrityOracle): self.psu = psu self.oracle = oracle def execute_test_scenario(self, timeout_sec: int = 60) -> bool: print("[Scenario] Generating 4KB Random Write Burst to trigger background GC...") start = time.time() while time.time() - start < timeout_sec: # VUC (Vendor Unique Command) / Telemetry Log 감시 internal_state = "GC_COPY_IN_PROGRESS" # 하드웨어 상태 폴링 if internal_state == "GC_COPY_IN_PROGRESS": print("[Trigger] Critical GC state detected! Injecting Power Loss in 30ms...") time.sleep(0.03) # 미세 레이스 컨디션 타이밍 윈도우 self.psu.cut_power() break time.sleep(1.0) # 커패시터 완전 방전 대기 self.psu.restore_power() print("[Boot] Waiting for Journal Replay & L2P Recovery (tBoot < 500ms)...") time.sleep(2.0) # 오라클 검증 return self.oracle.verify_lba_range(0, 100000) # 몬테카를로 무작위 타이밍 반복 검증 (수천 회 자동화) test = StateAwareGcPlpTest(PowerRelayController(), DataIntegrityOracle()) success = test.execute_test_scenario() print(f"[Result] Closed-Loop Test Status: {'PASS' if success else 'FAIL'}")
  • State-Aware Triggering: 단순 시간 지연(sleep) 방식의 테스트는 내부 상태와 엇갈립니다. VUC/SMART 텔레메트리 로그를 통해 FTL이 실제 GC 복사나 저널 플러시 상태에 진입한 순간을 포착하여 인젝션합니다.
  • Monte Carlo 회귀 시험: 정전 타이밍을 마이크로초 단위로 랜덤 지연시키는 몬테카를로 시뮬레이션을 통해 비동기 상태 머신의 잠재적 교착(Deadlock)과 메타데이터 손상을 100% 검출합니다.
